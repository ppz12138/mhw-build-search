# MHWilds 配装搜索器 —— 完整需求与交接文档

> 本文档供下一任接手 AI 使用。请先完整阅读，再动手。
> 最后更新：2026-08-18

---

## 一、项目概况

- **目录**：`mhw-build-search/`
- **核心文件**：
  - `fast_search_v3.py` —— 搜索算法（DFS + 剪枝），约 3200 行，**当前为正确版本**
  - `gui_server.py` —— GUI 服务器（启动图形界面用）
  - `index.html` —— 前端页面
  - `armors_cn.json` / `charms_cn.json` / `decos_cn.json` / `my_charms.json` / `skills_data.json` —— 游戏数据
  - `docs/source/sim-compiled-ja.js` —— 网页版配装器的**混淆压缩源码**（复刻目标）
  - `docs/wiki-db-algorithm-analysis.md` —— 早前对网页版算法的分析笔记
- **功能**：给定一组固定技能 + 组合技能（combo，如 黑蚀龙之力/霸主之魂），搜索防具/护石/珠子/武器的搭配，并支持：
  - **升级技能**（如 挑战者 3→4→5 各等级是否可达）
  - **追加技能**（从当前技能组出发，其他技能能加到几级）
  - 计算伤害、会心等指标

---

## 二、硬性需求（用户反复强调，不可违反）

1. **不能漏解**：网页版能搜到的合法配装，本工具必须也能搜到（30/30 覆盖）。任何"剪枝/聚合/支配过滤"一旦引入漏解即判失败。
2. **不能长耗时**：网页版跑完全部追加技能约 3 秒；本工具当前 ~255 秒，**必须对齐到网页版量级**。
3. **正确性优先**：宁可不加速，也不能为了速度牺牲正确性（漏解或误杀）。用户明确"正确的就去做"，批评过"反复迫降/中途质疑逻辑"。

## 三、当前状态（接手时的基线）

### 3.1 正确性（已验证通过）
- 用户组：`{挑战者3, 连击5, 精神抖擞3, 利刃3, 格挡性能3, 快吃3, 缓冲1, 耳塞2, 超会心3, 会心击【属性】3, 龙属性攻击强化3}` + combo `{霸主之魂3, 黑蚀龙之力2}` → 基线有解、挑战者可升级、黑蚀龙之力可达、超会心/连击可达。
- 陌生组（攻击流）：看破 3→5、匠 2→4 等可达。
- 关键修复历史：
  - **等价合并漏解** → 合并键加入 `slots_sorted`（按完整槽位分布，不是 slot_sum），修复 [3,1,0] vs [2,2,1] 被错误合并的问题。
  - **升级技能误判不可升级** → 升级/追加分支每级用 `test_fixed[sk]=lv` 重新构建候选池（需求维度一致，避免 q_score 剪枝 mis-fire）。
  - **α/β 变体漏解**（黑蚀龙护腿α vs β、祭典护腿α+ 等）→ `_variant_map` + `_expand_variants` 在记录解后按需求贡献分组展开变体。
- **当前剪枝**：`_greedy_deco_check_with_future` 里 `depth>=2` 用纯不乐观 `_check_deco_feasible`（确定技能 + 确定槽位）。

### 3.2 性能瓶颈（核心问题）
- 全技能追加/升级搜索 **~255 秒**（网页版 ~3 秒）。
- 瓶颈根因：**不可达技能**（如 属性攻击强化、瓶追撃、会心击【特殊】、各种强化）的 DFS 穷举到 timeout（单技能 5s）。
- 这些技能不可达的两种原因：
  1. **武器槽被固定武器技能占满**（用户组含超会心、会心击【属性】等武器技能，追加武器技能如会心击【特殊】没槽位）。
  2. **防具组合无法同时满足**所有固定技能 + 追加技能（技能分散在不同装备，组合不起来）。

## 四、为什么 Python 对不齐网页版（关键结论，勿重复踩坑）

### 4.1 网页版快的真正机制
网页版 `sim-compiled-ja.js` 的 `nb` 主搜索有三道核心剪枝（配合极小候选集）：
1. `A <= M`（递归前）：需求评分 ≤ 当前已选装备防御 → 否则剪。
2. `D.P.f * Pa + M < A`（候选层）：候选防御×剩余空槽 + 当前防御 < 需求评分 → break。
3. `Rb.b`（确定槽位珠子检查）+ `Dh/Eh/Fh`（精确珠子回溯）：当前已放装备 + 全部珠子能否满足剩余需求。

### 4.2 已确认的逆向难点（勿再浪费积分去猜）
- **`sim-compiled-ja.js` 是编译混淆的**，变量全为 `a/b/c/d`，字段映射（哪个是防御、哪个是评分、哪个是技能权重）无法可靠逆向。
- 多次尝试（he 权重表、DEF_WEIGHT、防御量纲）都因**量纲不确定**导致剪枝误杀基线（基线有解被判无解）。
- **结论：仅凭读混淆 JS，无法可靠复刻评分量纲。** 不要再尝试"猜一个量纲→测试→误杀→再猜"的循环。

### 4.3 已确认无法直接跑原版 JS
- `sim-compiled-ja.js` 是完整页面应用，依赖浏览器 `localStorage` / `DOM` / `preact` + 服务器 protobuf 数据（`ph`/`oh`/`gh` 从 `Ig(Ue/Ve/...)` URL 加载）。
- **node 环境无法离线直接运行**（需要网络下载游戏数据 + jsdom mock 浏览器，工程量大且易失败）。

### 4.4 已知数据事实
- `armors_cn.json` 和 `charms_cn.json` **都有 `defense` 字段**（如 公会十字腕甲α = 62，护石可为 0），武器数据无防御。
- 网页版 `Ud`（当前防御）、`wf`（需求评分）、`he`（技能权重）的具体实现未可靠确认。

## 五、已尝试并已排除的方案（勿重复）

| 方案 | 结果 |
|---|---|
| 双乐观上界剪枝（rsm 技能 + rsl 槽位） | 不剪（上界高估） |
| 纯不乐观 `_check_deco_feasible`（depth>=2） | **当前采用**，正确但慢（255s） |
| 精确珠子回溯 `exact_deco_feasible`（多技能场景） | 误杀（连超会心都判不可达） |
| 防御评分上界剪枝（`D.P.f*Pa+M < A`，DEF_WEIGHT 校准） | 误杀基线（量纲不确定） |
| Hb 技能权重表（表内1/表外100） | 误杀基线（量纲不确定） |
| 并行 `EXTRA_PARALLEL_WORKERS`（多进程） | spawn 下无效（pickle/重新加载数据开销） |
| node 直接跑原版 JS | 不可行（浏览器/服务器数据依赖） |

## 六、可行路径（给下任 AI 的建议）

### 路径 A：完整移植网页版 nb 搜索核心（唯一确定能对齐 3s 的路径）
- 需要**可靠确认网页版评分量纲**。建议：用网页版**在线实际运行**对照（用户可用网页版搜同一技能组，拿真实结果反推 `A`/`M` 数值），而不是猜。
- 移植 `nb`/`si` + `Dh/Eh/Fh` + `Rb.b` 到 Python，替换慢速 DFS。
- 关键：**极小候选集**（网页版等价合并极激进）+ **每层精确珠子回溯** + **评分上界**。
- 严格用用户组 + 陌生组 + 网页版对照验证不漏解。
- 风险：工程量中等偏大；若量纲确认无误，这是正解。

### 路径 B：保留当前正确版本（255s）
- 不做对齐，接受当前速度。
- 用户明确不满意，除非无路可走不建议。

### 路径 C：只修不可达技能的穷举（局部优化，风险可控）
- 针对"武器槽被固定武器技能占满导致追加武器技能不可达"的场景，**只对追加武器技能**判死（需区分固定 vs 追加，不能像之前那样用 `_deficit` 直接判，否则误杀）。
- 这是局部优化，可能把 255s 降到几十秒，但**达不到网页 3s**。

## 七、验收标准

1. **正确性**：
   - 用户组：挑战者可达、黑蚀龙之力可达、超会心/连击可达、所有固定技能满足。
   - 陌生组（攻击流）：看破 3→5、匠 2→4 可达。
   - 与网页版对同一技能组的搜索结果对比，**不漏解、不多出非法解**。
2. **性能**：全技能追加/升级搜索 ≤ 5 秒（目标对齐网页 3s）。
3. **代码**：新增/修改不破坏现有 GUI（`gui_server.py`）。

## 八、给下任 AI 的操作建议

1. **先跑通基线**：`python -c "import fast_search_v3"` 应加载数据无报错；`python _verify_final.py` 应正常输出（挑战者5组基线无方案，结构正确）。
2. **不要重复已排除的剪枝方向**（见第五节）。
3. **若走路径 A**：务必先拿到网页版真实运行结果做量纲反推，禁止猜。
4. **用户强调**：能对齐就对齐，不要"迫降"；做不到就诚实说明并给出可执行下一步。
